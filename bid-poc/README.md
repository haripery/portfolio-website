# bid-poc: Node.js + napi-rs vs Rust (axum) for a simple ad-bidding service

A reproducible latency/throughput comparison of two architectures that run **the same bidding code**:

- **A**: `server-node/`, a plain Node.js `node:http` server (no framework) that makes **one**
  synchronous napi-rs call per request (`engine-napi/`) into `engine-core/`.
- **B**: `server-rust/`, axum 0.8 + tokio, calling `engine-core/` directly.

[Part 2](#part-2-a-small-openrtb-26-image-bidder-real-world-traffic-shape) repeats the comparison with a small
OpenRTB 2.6 bidder for image ads, under traffic shaped the way an ad exchange sends it.

Every number in this README comes from a raw tool output saved under `bench/results/`. The
result tables are generated from those files by `bench/summarize.py` (Part 2: `bench/openrtb/summarize.py`), not
typed in. Nothing is estimated. All results were measured on one 4-vCPU KVM virtual machine (see
[Machine](#machine)). They describe that machine and this workload, not Node or Rust in general.

## Summary

**Part 1: one small request, closed loop.** All figures are measured: medians of 3 runs. Ranges, method and
caveats are further down.

- **Throughput.** With A as **one Node process** (round 1), B served **1.22×** A's requests/s at concurrency 1 and
  **2.83–3.23×** at concurrency 10–100. With A as a **2-worker Node cluster** (round 2), the gap was **1.22×** at c=1,
  rising to **1.67×** at c=100.
- **Latency at c=1** (no queueing): median **0.059 ms (A) vs 0.051 ms (B)**; p99 **0.201 vs 0.104 ms**.
- **The napi bridge is not where A's time goes.** Crossing JS↔Rust costs **0.32 µs** per call measured directly, or
  **0.49 µs** as a paired difference inside the same process. A spends **32.1 µs** of server CPU per request at c=100,
  so the bridge is about 1–1.5% of it. The Rust engine itself takes **2.6 µs** per call in isolation. In a V8 CPU
  profile of the loaded server, **55%** of the main thread's busy time is inside the native socket-write call and
  **15%** in Node's own JS HTTP/stream code; the request handler including the napi call is **23%**.
- **Per core.** Restricted to a single tokio worker thread, B still served **2.46×** A's single-process throughput at
  c=100, using **12.9 vs 32.1 µs** of CPU per request.
- **Memory.** B **7.5 MB** RSS. A **81.2 MB** RSS as one process; **200.1 MB** RSS (125.5 MB PSS) as a cluster.
- **Errors.** **0** errors and **0** non-200 responses across all 81 HTTP runs.
- **An anomaly.** In **3 of 9** runs at c=100, B ran in a slow mode for the whole run (62,965–89,067 vs
  121,900–126,694 req/s). The cause is not known; see [Analysis](#analysis).
- **Main caveat.** Client and server share one 4-vCPU VM over loopback, and the VM's CPU speed fluctuates. These
  numbers describe this setup only.

**Part 2: an OpenRTB 2.6 image bidder, open loop.** All figures are measured: medians of 2 runs (micro-benchmark:
3 runs; memory: 1 run).
Details in [Part 2](#part-2-a-small-openrtb-26-image-bidder-real-world-traffic-shape).

- **Meeting the deadline.** Requests were offered at a fixed rate and given up after 100 ms, as an exchange does.
  B had **0** timeouts at every rate tested, up to **55k req/s** (p99 11.99 ms). In 30 s, one Node process timed
  out on **78,356** requests at 25k req/s, and the Node cluster on **121,958** at 40k req/s.
- **Cold start.** A fresh server with no warm-up, offered 10k req/s for 10 s: **1,186** timeouts (Node single
  process), **3,270** (Node cluster), **12** (B).
- **CPU per request** at c=100: **51.8 µs** (Node single process), **44.0 µs** (Node cluster), **37.0 µs** (B). The
  JS→Rust call accounts for **2.03 µs**. With 200,000 line items the engine's own work dominates, and A and B
  came within 5% of each other.
- **Memory** (RSS) with 200,000 line items: **172.8 MB** (Node single process), **385.3 MB** (Node cluster),
  **120.2 MB** (B).
- **Same output.** A and B returned byte-identical responses to all 1,008 test requests.
- **Recommendation** (a judgement, not a measurement): Rust for the bid-request path, with Node a reasonable choice
  for the APIs around it. See [the Part 2 analysis](#part-2-analysis-real-world-problems-and-which-architecture-fits-openrtb).

## The bidding logic (`engine-core`)

- **Input** (`POST /bid` body): `{ "id", "slot": {"w","h"}, "device": "mobile"|"desktop"|"tv", "url", "user_segments": [string] }`.
  Unknown extra fields are ignored. Malformed JSON, missing fields or an unknown device give HTTP 400 with
  `{"error":"invalid bid request: …"}`. That error body is built by engine-core, so both servers send the same bytes.
- **Advertisers**: 1,000, generated at start-up from fixed seed `42` with a self-contained SplitMix64 PRNG. The
  generator uses integer arithmetic only, so the list does not depend on a `rand` crate version. Each advertiser
  has an id (`adv-0001`…), 1–3 allowed sizes out of 8 IAB sizes, a non-empty subset of the 3 devices, 1–5 target
  segments out of a 48-segment vocabulary, a base CPM of 0.50–12.00 in whole cents, a click URL and an image URL.
- **Pipeline** (`Engine::bid_json(&str)`):
  1. parse the request with serde_json;
  2. filter eligible advertisers on size and device, using bitmasks precomputed at start-up;
  3. score each one: `price = base_bid × (1 + 0.25 × matching segments)`, with matches capped at 4 (so at most 2.0×).
     The arithmetic is exact integer micro-currency;
  4. pick the highest score. Ties go to the lowest advertiser index;
  5. build the HTML creative: an image inside a click-through link, a 1×1 impression pixel, and an inline
     viewability script (IntersectionObserver: at least 50% visible for 1 s fires a beacon). Request-supplied
     values are HTML-escaped in attributes and percent-encoded in URLs;
  6. serialize `{ request_id, advertiser_id, price, html }`.
  If no advertiser is eligible the result is "no bid", sent as HTTP 204 with an empty body.
- For the benchmark payload there are **154 eligible advertisers**; the winner is `adv-0330` at price `15.21`, and the
  response is **1,179 bytes** (output of `cargo run --release -p engine-core --example inspect`).
- **Tests** (`cargo test -p engine-core`, output in `bench/results/unit-tests.txt`):
  - golden winners for 4 fixed inputs, plus one no-bid input. The golden values were recorded from the
    `inspect` example and pin the behaviour;
  - same seed → identical advertiser list and identical output bytes; a different seed → a different list;
  - the bitmask fast path is compared with a deliberately naive string-matching reference implementation on
    5,000 pseudo-random requests;
  - escaping, the response key order, the scoring rule and error handling.

## Design choice for A: what crosses the JS ↔ Rust boundary

Node passes **the raw HTTP body as one JS string** to one synchronous napi function and gets the response back as
one JS string (`bid(requestJson: string): string | null`; it throws on invalid input):

- JSON is parsed **in Rust** (serde_json). Node does not parse it, and no JS objects are converted field by field
  across the boundary. Per request there is exactly one boundary crossing, and its cost is two string copies: the
  JS string is transcoded to UTF-8 into a Rust `String` (`napi_get_value_string_utf8`), and the Rust `String`
  becomes a new V8 string (`napi_create_string_utf8`).
- The call is synchronous on the event-loop thread. engine-core does a few microseconds of CPU work per request
  (see Benchmark 1), so handing it to the libuv thread pool would cost more in thread hand-off than it saves.
- `engine-napi` also exports **probe functions** (`probeNoop`, `probeTakeString`, `probeSetEcho`/`probeEcho`,
  `probeEngineLoop`). Only the micro-benchmark uses them, to split the cost of `bid()` into boundary and engine; the
  server never calls them.

## Fairness rules and how they are enforced

| Rule | How |
|---|---|
| Same bidding logic | Both servers link the same `engine-core` crate from one Cargo workspace (one `Cargo.lock`). `bench/results/build-flags.txt` shows the rustc command line for engine-core in both builds: `-C opt-level=3 -C embed-bitcode=no -C strip=debuginfo`. The only difference is `--target x86_64-unknown-linux-gnu`, which the napi CLI passes and which is the host triple. |
| Release builds | `cargo build --release` for server-rust and `napi build --release` for the addon, both with Cargo's default release profile (no LTO, codegen-units or allocator tuning on either side). |
| Logging off | No per-request logging in either server. Each prints one line to stderr at start-up. axum is built without its `tracing` feature. |
| Same port style, protocol and payload | Both listen on `127.0.0.1` (A on :3001, B on :3002), speak HTTP/1.1 with keep-alive, and have Nagle disabled (`noDelay: true` / `set_nodelay(true)`). Every request is `bench/payload.json`, sent by oha with `-D`. |
| Same response | `bench/verify.sh` sends 9 requests (normal bids, escaping and unicode, no-bid, 3 kinds of invalid input) to both servers and compares status, content-type and body bytes. Result: **all 9 identical** (`bench/results/verify.txt`). Headers are not identical: Node also sends `Connection: keep-alive` and `Keep-Alive: timeout=5`, which are Node defaults and were left alone. |
| Node single process vs Rust default runtime | Round 1: `node server.js` (one process, no cluster) against `#[tokio::main]` (multi-thread runtime, default worker count). |
| Not single-core vs multi-core by accident | Round 2: `node cluster.js`, with one worker per `os.availableParallelism()` CPU, against the same Rust server. A supplementary run also limits Rust to one tokio worker. |
| Client must not steal server CPU | The VM has 4 vCPUs, so the **servers are pinned to CPUs 0–1** and **oha (2 worker threads) plus the samplers to CPUs 2–3** (`taskset`). "All cores" therefore means the **2 CPUs the server may use**: tokio starts 2 workers and the Node cluster forks 2 workers (both detect the 2-CPU affinity; the start-up lines are in each run's `server.log`). oha's own CPU use is recorded so a client-bound run can be spotted. |
| Warm-up, then measure | Every cell (configuration × concurrency) starts a **fresh server**, runs a 10 s oha warm-up (saved as `warmup.json`, not used in the tables), then a 30 s measured oha run. |
| Repeatability | The whole suite runs **3 times**, with A and B interleaved at each concurrency level. The order is reversed on the 2nd repetition, so neither side always goes first. Tables show the median of the 3 runs and the min–max range. |
| No artificial errors | oha runs with `-w`, so requests still in flight at the deadline complete instead of being counted as "aborted due to deadline" errors. |
| Micro-benchmark (bridge alone) | criterion (`engine-core/benches/engine.rs`) and `bench/napi-bench.js` use the same `bench/payload.json` and are pinned to the servers' CPUs 0–1. They alternate 3 times. The Node harness interleaves its samples: each round takes one ~50 ms sample of every benchmark. It also runs **`probeEngineLoop`**, which loops the engine inside Rust *inside the Node process*, so `bid()` can be compared with the engine alone in the same process, on the same CPUs, at the same time. |

**Why so much repetition.** This VM's CPU speed is not stable. `bench/vcpu-speed-check.sh` runs the engine in a tight loop
and prints ns/iteration every 250 ms. It shows each vCPU switching, independently of the others, between a faster and a
slower speed for multi-second stretches (the numbers are in the Diagnostics section of the results). Two measurements taken
at different times can therefore differ even when nothing else changed. That is why the runs are repeated and interleaved,
and why the tables report ranges.

## How to run

Prerequisites: Linux with `taskset` (util-linux), Rust (tested with 1.97.0), Node ≥ 18.14 (tested with v22.23.5;
`os.availableParallelism()` is needed), python3, curl, and oha. oha was not installed on this machine; it was installed with
`cargo install oha --locked --version 1.17.0`. The napi CLI (`@napi-rs/cli` 3.11.1) is a local devDependency of
`engine-napi/`; there is no global install.

```bash
cd bid-poc
(cd engine-napi && npm ci && npx napi build --platform --release)   # -> engine-napi/engine-napi.linux-x64-gnu.node
cargo build --release -p server-rust                                # -> target/release/server-rust
bench/run-all.sh       # everything below, in order (took 59.5 min here: 02:19–03:18 UTC); rewrites bench/results/ and the tables in this README
```

Or step by step:

```bash
cargo test -p engine-core --release          # unit tests
bench/verify.sh                              # A and B must return identical bodies (exits 1 if not)
bench/run-micro.sh                           # benchmark 1: criterion + napi micro-benchmark
bench/run-http.sh                            # benchmarks 2 + 3 (env: REPS LEVELS WARMUP DURATION SERVER_CPUS CLIENT_CPUS ...)
bench/profile-node.sh                        # diagnostic: V8 CPU profile of A under concurrency 100
bench/vcpu-speed-check.sh                    # diagnostic: is the VM's CPU speed stable / equal across vCPUs?
RESULTS=bench/results/followup-round1-c100/http PHASES=round1 LEVELS=100 REPS=3 bench/run-http.sh   # the follow-up
python3 bench/summarize.py --readme README.md
node server-node/server.js                   # A on :3001   (cluster: node server-node/cluster.js)
target/release/server-rust                   # B on :3002
curl -s -X POST --data-binary @bench/payload.json http://127.0.0.1:3001/bid
```

Part 2 (OpenRTB), after the two build commands above:

```bash
bench/openrtb/run-all.sh       # everything in Part 2, in order (took 31 min here: 15:48–16:19 UTC); rewrites bench/results/openrtb/ and the Part 2 tables
```

Or step by step:

```bash
cargo test -p engine-core --release           # includes the 8 OpenRTB tests
bench/openrtb/make-inputs.sh                  # writes bench/openrtb/corpus.jsonl (1,000 requests, seed 7; not committed)
bench/openrtb/verify.sh                       # A and B must return identical responses to 1,008 requests
bench/openrtb/run-micro.sh                    # criterion + napi micro-benchmark
bench/openrtb/run-load.sh                     # closed loop, open loop, cold start, memory (env: PHASES OPEN_RATES TMAX ...)
python3 bench/openrtb/summarize.py --readme README.md
curl -s -X POST -H 'content-type: application/json' \
  --data-binary @engine-core/fixtures/openrtb-2.6/example-1.json http://127.0.0.1:3002/openrtb2/bid
```

## Analysis

Each statement is labelled **[measured]**, meaning it is a number from the tables above or from the raw file named next
to it ("derived" marks plain arithmetic on measured numbers), or **[explanation]**, meaning my interpretation, which was
not measured here.

### 1. Throughput and latency, A vs B

- **[measured]** Round 1 (A = one Node process): B served **1.22×** A's requests/s at c=1 and **3.06×, 3.23×, 2.83×** at
  c=10/50/100. A plateaus at 29,214–33,324 req/s from c=10 upwards while its process uses **100–101% CPU**, i.e. one core.
  Derived check: 1 s ÷ 31,452 req/s = 31.8 µs per request, close to A's measured 32.1 µs of CPU per request at c=100.
- **[measured]** Round 2 (A = Node cluster, 2 workers, **197–198% CPU** at c=100): the gap narrows to **1.22×, 1.27×, 1.49×,
  1.67×** at c=1/10/50/100. The cluster served 2.34× (c=10) and 2.39× (c=100) the throughput of the single process. At
  c=1 the cluster is the same as the single process (14,898 vs 14,641 req/s). *[explanation]* oha's single connection
  is handed to one worker, so the second worker sits idle.
- **[measured]** Latency at c=1 (no queueing): p50 **0.059 ms (A) vs 0.051 ms (B)**, p99 **0.201 vs 0.104 ms**,
  p99.9 **0.567 vs 0.255 ms**. A's median is 8 µs higher and its tail roughly 2× longer. *[explanation]* A's longer tail
  fits occasional V8 garbage-collection pauses. I did not take a GC trace, so this is not verified.
- **[measured]** At c≥10 the latency ratios follow the throughput ratios. Derived check with Little's law:
  100 connections ÷ 31,452 req/s = 3.18 ms against A's measured p50 of 3.097 ms, and 100 ÷ 125,119 = 0.80 ms against
  B's 0.772 ms (round 2). *[explanation]* In this closed-loop test, high-concurrency latency is mostly time spent waiting
  in the server's queue, so it is not independent evidence beyond throughput.
- **[measured]** No transport errors and no non-200 responses in any of the 72 HTTP runs (plus 9 follow-up runs).

### 2. Where the time goes in A

The per-request picture, in one place:

| Part of A's per-request cost | Value | Source | Label |
|---|---:|---|---|

| napi boundary: request JS string → Rust `String` (210 B) | 129.5 ns | `probeTakeString` − `probeNoop` | derived |
| napi boundary: response Rust `String` → JS string (1,179 B) | 147.2 ns | `probeEcho` − `probeTakeString` | derived |

| Node's JS HTTP / stream / event code | 4.31 µs | V8 profile (sum of the JS categories) | measured (profiler; grouping is mine) |
| native `writev` (socket write) | 15.50 µs | V8 profile | measured (profiler) |
| `(program)`: native code outside JS, including llhttp and libuv | 0.93 µs | V8 profile | measured (profiler) |
| V8 garbage collector (main thread) | 0.47 µs | V8 profile | measured (profiler) |
| **total main-thread busy time per request** | **28.15 µs** | V8 profile | measured (profiler) |

- **String copy across napi.** **[measured]** The boundary costs **315.6 ns** per call (`probeEcho`): 38.9 ns for the
  bare call, 129.5 ns to bring the 210-byte request into Rust, and 147.2 ns to turn the 1,179-byte response into a V8
  string. These Node figures include about 10.6 ns of harness overhead per call (the `js: () => 1` row). The paired,
  same-process difference `bid()` − `probeEngineLoop` is **486.3 ns**, a bit more than `probeEcho`. **[derived]** The
  boundary is therefore 9–14% of one `bid()` call, but only **about 1–1.5% of A's 32.1 µs of CPU per request**.
  *[explanation]* Passing one string each way keeps the boundary cheap. Converting JSON into JS objects, or making
  several calls per request, would cost more; that alternative was not measured.
- **JSON parse in Rust.** **[measured]** 371.2 ns, or 14% of the 2,610.5 ns engine pipeline (derived). The most
  expensive engine stage is serializing the response (1,050.6 ns, 40%). *[explanation]* It has to JSON-escape the
  ~1.1 KB HTML string, which is full of `"` characters.
- **The engine costs more inside the server than in a loop.** **[measured]** Inside the profiled server, the handler that
  calls `bid()` takes 6.60 µs per request, 1.9× the 3.46 µs of the tight loop. Removing the call entirely (the A-stub
  server) cuts CPU per request from 32.1 to 21.0 µs, i.e. by 11.1 µs (derived). Note that the stub and the real server
  ran at different times, so this difference includes run-to-run variation. The same appears in B: B-stub 9.6 µs vs
  B 15.7 (round 2) or 20.9 µs (round 1) per request, while the engine costs 2.61 µs in criterion. I also measured the
  engine running **356 ns slower inside the Node process** than under criterion (`probeEngineLoop` vs criterion,
  consistent across all 3 runs). *[explanation]* In a busy server, the kernel network stack and the HTTP code run
  between engine calls and evict the engine's data and code from the CPU caches, so each call starts "cold". None of
  these numbers isolates that effect, and the two estimates (6.6 µs from the profile, 11.1 µs from the stub) disagree.
- **"HTTP parsing in JS".** *[explanation]* Node's HTTP/1 parser is **llhttp, a C library**. Node runs it from C++ as
  socket data arrives, and it calls into JS for each request (`parserOnHeadersComplete`, `_addHeaderLine`, the `'data'`
  and `'end'` events). The response is built in JS (`writeHead`, `_storeHeader`, header validation) and written through
  Node streams. **[measured, profile]** Node's own JS (HTTP layer, net/streams, EventEmitter, Buffer, other Node
  internals, and the parts of `server.js` other than the `'end'` handler) costs 4.31 µs per request (15.3% of
  main-thread time). `(program)`, which includes llhttp and libuv, is 0.93 µs (3.3%). GC is 0.47 µs (1.7%).
- **The socket write is the largest single item.** **[measured, profile]** The native `writev` function accounts for
  55.1% (15.50 µs per request). *[explanation]* V8 charges time spent inside a syscall to the native function that made
  it. On loopback that includes the kernel's TCP send path and delivery into oha's socket. I could not split it further,
  because `perf` is not available here. It is also unclear why this costs A more than B's *entire* request (B used 15.7
  µs of CPU per request in round 2); profiler overhead on syscalls is one possibility. Treat this row as the least certain.
- **Event loop.** **[measured]** At c=100, A's single process uses 100–101% CPU, and its throughput stops rising after
  c=10 (29,214 → 33,324 → 31,452 req/s at c=10/50/100). In the profiled run the main thread was busy 34.4 s of its
  40.6 s lifetime. Under steady load it was **idle (waiting for events) in 11–18% of each second**. The exceptions are
  25% in the second containing the switch from warm-up to the measured run, and 74% in the final second. These
  per-second idle fractions were computed from the profile's own samples. *[explanation]* Every connection's JS work runs one piece
  at a time on that one thread, so A cannot use the second CPU to handle requests. The thread is busy about 85% of the
  time while the process uses about 100% of a CPU; the difference is presumably V8's helper threads (GC, compiler),
  but per-thread CPU was not recorded. The idle gaps suggest that, in this closed loop, the thread sometimes runs out
  of queued requests while oha is still turning responses around.

### 3. Why B differs

- **[measured]** B runs its handlers on both CPUs: 186% CPU (round 1) and 196% (round 2) at c=100. That accounts for
  part of the round-1 gap.
- **[measured] Per core, B is still cheaper.** With one tokio worker (B′), B uses one core like A (99% vs 100% CPU at c=100)
  and serves **77,282 vs 31,452 req/s (2.46×)** at **12.9 vs 32.1 µs of CPU per request (2.49×)**. With both sides on
  2 CPUs (round 2, c=100) B uses 15.7 µs per request against A's 26.4 (1.68×).
- **[measured] Even without the engine, Node's HTTP path costs more.** At c=100, A-stub uses 21.0 µs of CPU per request
  against 9.6 µs for B-stub (2.19×). Caveat: during the B-stub runs oha was at 184–188% of its 200% CPU budget, so
  B-stub's *throughput* may have been limited by the load generator. Its CPU per request is still valid.
- *[explanation]* Why B is cheaper per request:
  - Per request, A switches between C++ and JS several times: llhttp calls into JS, JS calls into napi, then into the
    native `writev`.
  - A allocates JS objects per request (`IncomingMessage`, `ServerResponse`, header arrays, closures, Buffer chunks,
    strings) that the GC must later collect.
  - A converts the bytes several times: Buffer → JS string → UTF-8 Rust `String` → Rust `String` → V8 string → bytes
    again in `writev`. In B the request bytes are checked once as UTF-8 and lent to the engine as `&str`, and the
    response `String` is moved into the HTTP body without a copy.
  - hyper's parser and response encoder are compiled Rust, with no callbacks into a JS VM.
  - Kernel work (syscalls, loopback TCP) is about the same per request on both sides.
- **[measured] Two workers cost B some efficiency.** B′ (one worker) needs less CPU per request than B (two workers):
  29.1 vs 41.0 µs at c=1, and 12.9 vs 15.7–20.9 µs at c=100. *[explanation]* The two workers have to coordinate
  (waking each other, stealing work), which costs CPU, most visibly when the load is light.
- **[measured] B has an unexplained slow mode.** In round 1, 3 of 6 B runs at c=50/100 were slow for their **whole 30 s**:
  62,965–89,067 req/s, with the server **not** saturated (176–187% CPU) and 20.9–28.0 µs of CPU per request. The
  other 9 B runs at c=50/100 reached 106,336–126,624 req/s at 193–197% CPU and 15.5–18.2 µs per request. A follow-up
  ran the round-1 c=100 sequence 3 more times (`bench/results/followup-round1-c100/`) and B was slow again in 1 of 3
  (75,320 req/s, 180.4% CPU, 23.9 µs per request; the others were 126,694 and 125,290). Overall that is 3 of 9 B runs at
  c=100. It never happened to B′ (one worker, 6 of 6 runs at c=100), to A (6 of 6 single-process runs and 3 of 3
  cluster runs at c=100; worst single-process run 30,122, best 33,044 req/s), or to B in round 2. **The cause is not known.** *[explanation, unverified]* Two candidates: interference from the host (the
  vCPU check shows each vCPU's speed changes for seconds at a time), or the two tokio workers settling into an
  inefficient pattern of sleeping and waking each other when not fully saturated. That is why round 1's median for B at
  c=100 (89,067) is far below round 2's (125,119) for the identical server. Even B's slowest run was about 1.9× A's
  fastest round-1 run at c=100 (62,965 vs 32,964).

### 4. Memory (c=100 runs)

- **[measured]** B: **7.5 MB** RSS in both rounds (PSS 5.5 and 5.4 MB). A single process: **81.2 MB** RSS (79.3 MB PSS). A cluster:
  **200.1 MB** RSS summed over its 3 processes, **125.5 MB** PSS. RSS double-counts the pages the processes share;
  PSS does not. *[explanation]* Most of A's memory is the Node runtime and V8 heap, once per process. The cluster runs a
  primary process plus a full runtime per worker. The 1,000-advertiser list itself is small in both.

### 5. How much to trust these numbers

- **[measured]** Run-to-run spread is substantial on this VM. The vCPU check shows per-iteration speed on each vCPU
  ranging from about 2,050 ns to over 4,000 ns, with medians of about 2,640–2,720 ns. The same server also needed
  15.5–28.0 µs of CPU per request in different runs (B at c=100). Interleaving, alternating order and medians of 3
  reduce this noise but do not remove it.
- **[measured]** oha used at most 146.8% of its 200% CPU budget in any run except the B-stub runs (184–188%). VM steal
  time stayed at or below 0.97% in all 81 runs. *[explanation]* So the load generator is unlikely to have limited any
  result except B-stub's throughput.
- *[explanation]* The direction and rough size of every A-vs-B result in the tables are larger than this noise. For
  example, at c=1 A's best run (15,257 req/s) is below B's worst (17,601). Small differences, such as round-1 vs
  round-2 values for the same server, are not.

## What happened along the way (nothing hidden)

- The napi CLI builds with an explicit `--target`, so engine-core is compiled twice. `build-flags.txt` shows the two
  rustc command lines are the same apart from that flag.

## Part 2: a small OpenRTB 2.6 image bidder (real-world traffic shape)

Part 1 sent one tiny request again and again, in a closed loop. A real bidder works differently:
- it receives OpenRTB 2.6 bid requests at a rate the exchange chooses (an open loop);
- it must answer within `tmax`, after which an answer is worthless.

Part 2 is a **deliberately small OpenRTB bidder for image (banner) ads only**, used to measure A and B under that

### Part 2 analysis: real-world problems and which architecture fits OpenRTB

The labels are the same as in Part 1: **[measured]** means a number from the tables above or a named raw file
("derived" marks arithmetic on measured numbers), and *[explanation]* means my interpretation.

**1. With traffic sent the way an exchange sends it, B keeps answering in time when A cannot.**
- **[measured]** Open loop with a 100 ms timeout per request:

| offered | A single process | A cluster | B |
|---:|---|---|---|
| 10k req/s | no timeouts, p99 8.18 ms | no timeouts, p99 2.99 ms | no timeouts, p99 1.05 ms |
| 25k req/s | 78,356 client timeouts; median latency of answered requests 251.10 ms, i.e. overloaded | 4,080 timeouts (0–8,160 across the two runs); p99 114.93 ms | 0 timeouts; p99 2.24 ms |
| 40k req/s | 84,051 timeouts; answered 53.36% of what was offered | 121,958 timeouts; answered 76.72% | 0 timeouts; p99 10.41 ms, p99.9 21.05 ms |
| 55k req/s | answered 37.98% of what was offered | answered 49.31% | answered 100.00% with 0 timeouts; p99 11.99 ms, p99.9 38.68 ms, at 165% CPU |

- **[measured]** The cluster lost 121,958 requests at 40k req/s even though its closed-loop throughput at c=100 is
  44,729 req/s.
- *[explanation]* A closed loop is forgiving: when the server slows down, the client waits. An exchange doesn't
  wait. Requests keep arriving, so once the server falls behind its queue grows and answers start missing `tmax`.
  What decides lost auctions is headroom below the offered rate, not peak throughput. The spec has a name for
  this case: OpenRTB 2.6's `nbr` field uses OpenRTB 3.0's list of no-bid reasons, where code 15 is "Insufficient
  Auction Time".
- *[explanation]* The "answered" share flatters an overloaded server. When all 500 connections are busy, oha holds
  a request back before sending it, and the 100 ms timeout only starts when it is sent. That is why A single at
  25k req/s shows 85.84% answered while the median answered request took 251.10 ms counted from when it should
  have been sent. An exchange would count most of those as late.

**2. Where A's extra time goes: still not the bridge.**
- **[measured]** The engine costs 10.52 µs per OpenRTB request when called directly (criterion). Parsing the
  691-byte average request alone is 1.52 µs. A per-stage timing (`diagnostics/engine-breakdown.txt`, 3 runs)
  gives parse 1.60–1.69 µs, decide 6.26–6.52 µs and render + serialize 1.62–1.69 µs.
- **[measured]** Called through napi from Node it costs 13.65 µs. The same engine looped inside the Node process
  costs 11.59 µs, so crossing the boundary adds **2.03 µs** per request (paired, same process).
- **[measured]** Server CPU per request at c=100 is 51.8 µs for A single, 44.0 µs for A cluster and 37.0 µs for B.
  **[derived]** That is 14.8 and 7.0 µs more per request than B; the bridge accounts for 2.03 µs of it.
  *[explanation]* The rest is Node's HTTP and event-loop machinery, as Part 1 found.
- **[measured]** That gap is a fixed cost per request, so it matters less when the bidding work is heavy. With
  200,000 line items (one run each) CPU per request was 1,182.1 µs (A single), 1,195.2 µs (A cluster) and
  1,142.3 µs (B). The cluster served 1,653 req/s against B's 1,727. **[derived]** A is within 5% of B on both
  counts, no more than the run-to-run spread of other cells in these tables. *[explanation]* This POC scans every
  line item of the requested size, so the engine's cost grows with the number of line items. At 200,000 items
  Rust's own work dwarfs the tens of microseconds that Node's HTTP layer adds. The architecture choice therefore
  matters most when the bidding logic is cheap and the request rate is high. A real bidder would use a more
  selective index, but might add heavier work such as model scoring. Where a real bidder falls between these two
  cases was not measured here.

**3. Every restart costs A timeouts.**
- **[measured]** Cold start, 10k req/s for 10 s with no warm-up:

| | A single | A cluster | B |
|---|---:|---:|---:|
| timeouts | 1,186 (513–1,859) | 3,270 (2,508–4,032) | 12 (0–24) |
| p99 | 18.41 ms | 11.95 ms | 1.21 ms |

- *[explanation, not verified]* The likely cause is V8's warm-up: it starts by interpreting the JavaScript and
  optimizes hot code while it is already serving traffic, whereas B is compiled ahead of time. The burst of 500 new
  connections at the start may also play a part; I did not separate the two. Either way, every deploy,
  crash-restart or autoscaling event would pay this as requests that miss `tmax`.

**4. Memory grows with each Node process.**
- **[measured]** With 2,000 line items at c=100: A single 85.0 MB, A cluster 192.8 MB RSS (119.6 MB PSS),
  B 8.5 MB.
- **[measured]** With 200,000 line items: A single 172.8 MB, A cluster 385.3 MB RSS (312.2 MB PSS), B 120.2 MB.
- *[explanation]* Each cluster worker is a separate process holding its own copy of the line-item index, because
  the Rust addon's data lives inside each process. B has one copy shared by all its threads. Real DSPs also keep
  budgets, frequency caps and user data, so the duplication grows, or that state has to move to an external store.

**5. Two lessons from the larger version** (raw data in `bench/results/openrtb-full-v0/`):
- **[measured]** Passing the request as a string or as a zero-copy `Buffer` made no measurable difference at
  2.4 KB requests (26.02 vs 26.21 µs per call). "Zero-copy" didn't pay off here.
- **[measured]** Allocating gzip state per request cost the multi-threaded Rust server 31.30 page faults and
  155.4 µs of CPU per request (12,844 req/s). Reusing that state per thread brought it to 0.00 page faults, 58.4 µs
  and 34,197 req/s. Keeping the per-request allocation but raising glibc malloc's trim and mmap thresholds to
  64 MiB also removed the faults (32,916 req/s). *[explanation]* glibc was handing the large compression buffers
  back to the kernel after each request and faulting them in again on the next. Rust is not automatically fast;
  only measuring showed this.

**Other real-world problems** *[explanation, not measured here]*:

- **A: Node + napi**
  - JavaScript runs on one thread per process, so using more cores means more processes. Shared state such as
    budgets, pacing and frequency caps then needs an external store or inter-process messaging.
  - The garbage collector can pause the event loop, which hurts tail latency. Part 1's longer tail for A (p99.9 at
    c=1: 0.567 ms against 0.255 ms for B) fits that, but no GC trace was taken.
  - A synchronous napi call blocks every other request while it runs. If the bidding logic gets heavier (e.g.
    model scoring), it must move to the libuv thread pool, which adds a hand-off on every call.
  - Native-addon operations: prebuilt binaries per platform (glibc vs musl, x64 vs arm64), two toolchains, and a
    crash in native code takes the whole process down.
  - JavaScript numbers are floating point, while the spec recommends integer math for prices (4.2.3). Keep pricing
    in Rust.
- **B: Rust**
  - The team needs Rust skills, and compile times are longer.
  - Blocking work inside an async task stalls a tokio worker. Part 1's unexplained slow mode shows the runtime and
    the OS can still surprise.
  - Less shared code to reuse: Prebid Server, the open-source server-side auction that sends OpenRTB requests to
    bidders, has Go and Java implementations, not Rust. That comes from a web-search summary; docs.prebid.org was
    blocked by this environment's network policy, so I couldn't check the page itself.
- **Both**
  - `tmax` includes the network round trip ("including Internet latency", 3.2.1). A bidder far from the exchange
    loses most of its budget before computing anything, so placement near the exchange matters at least as much as
    the language.
  - Exchanges throttle bidders that time out often, per a web-search summary of Google's Authorized Buyers docs.
    developers.google.com was blocked here, so this is not verified.

**Which is better for an OpenRTB bidder, and why** *[judgement, based on the measurements above]*:

- **Use B (Rust) for the bid-request path.** In these measurements it:
  - had 0 client timeouts at every offered rate up to 55k req/s. One Node process had timeouts from 25k req/s
    on; the Node cluster had them in one of its two runs at 25k and in every run from 40k on;
  - lost 12 requests (0–24) in the cold-start test, against 1,186 and 3,270 for the two Node setups;
  - used **16% less CPU per request than the Node cluster and 29% less than one Node process** at c=100 with
    2,000 line items (derived: 37.0 ÷ 44.0 and 37.0 ÷ 51.8);
  - used less memory: 8.5 MB RSS against 85.0 and 192.8 MB with 2,000 line items, and 120.2 MB against 172.8
    and 385.3 MB with 200,000.
  On an exchange, that means more bids arrive before `tmax` and fewer servers carry the same traffic. The CPU
  advantage shrinks when the bidding logic itself is heavy (point 2).
- **A (Node + Rust via napi) is a reasonable choice when:**
  - the team is JavaScript-first;
  - traffic per process stays well below its limit (here, 10k req/s was fine for one process and 25k was not);
  - or for the control plane: campaign management, reporting, creative upload.
  The napi bridge itself is cheap; the cost is Node's HTTP layer and the process model.
- **A practical split:** Rust for the bidder's hot path (bid requests, win and billing notices) and Node for the
  APIs and UIs around it.

### What happened along the way in Part 2

- **Sources.** The spec was read from the IAB Tech Lab repositories on GitHub: OpenRTB 2.6 and its implementation
  guide, plus OpenRTB 3.0 for the no-bid reason list it references. Two other sources were **blocked by this
  environment's network policy**: developers.google.com (Google's Authorized Buyers documentation) and
  docs.prebid.org. What the analysis says about them comes from web-search summaries only and is labelled that way.
- **A larger first version.** I first built a bigger POC (commit `e80791b`): banner **and** video (VAST), gzip in
  both directions, privacy gating, no-bid reason codes, floor currency conversion, and 10,000 requests of about
  2.4 KB. You then asked for image ads only and a smaller example, so it was cut down (commit `4b239e2`) and every
  Part 2 measurement was taken again. The larger version's raw results are kept in
  `bench/results/openrtb-full-v0/` (see its `NOTE.md`). Only the two findings in point 5 of the analysis come from
  it.
- **The gzip slowdown** (larger version). With gzip, the Rust server at first served no more requests than one
  Node process (12,844 vs 12,385 req/s) while using about twice the CPU per request (155.4 vs 81.8 µs). A
  page-fault comparison (`openrtb-full-v0/diagnostics/gzip-alloc.txt`) traced it to allocating compression state
  per request. Reusing that state per thread fixed it, and the larger version's reported tables use the fixed code.
- **A wrong column label, corrected.** The open-loop column was first called "answered within 100 ms". That was
  wrong: oha starts the 100 ms timeout when a request is sent, not when it was due, so a request can count as
  answered and still be far later than 100 ms. The column was renamed and the note above the table explains it.
  No numbers changed.
- **Stale micro-benchmark data, removed.** `bench/openrtb/run-micro.sh` copied every criterion result under
  `target/criterion/openrtb/`. That included benchmarks left over from the larger version, last written at 04:49
  UTC, while this run started at 15:48 UTC. They were deleted from `bench/results/openrtb/micro/` after the run,
  and the script now clears that directory first. Part 1's `run-micro.sh` had the same weakness; it now copies only
  its own benchmarks. Part 1's results were not affected: they contain only Part 1's own benchmarks (checked).
- **Provenance.** Every Part 2 measurement ran from commit `11605aa`, with only `README.md` modified
  (`bench/results/openrtb/provenance.txt`). After the run, `bench/openrtb/summarize.py` (the column label) and both
  `run-micro.sh` scripts (the fix above) changed. `summarize.py` only reads raw files.
- **Fewer repetitions than Part 1.** Each Part 2 cell ran twice (memory: once), not three times, to keep the whole
  run to about half an hour.

## Caveats (read these before quoting any number)

- **One VM, loopback.** oha and the servers share one 4-vCPU KVM guest and talk over `127.0.0.1`. CPU pinning
  separates them, but they still share the L3 cache, memory bandwidth and the kernel network stack. There is no
  network round-trip, so per-request server overhead counts for far more here than it would behind a real network.
- **"All cores" means 2 cores**: the server cpuset is 0–1, because the other two vCPUs run the load generator.
- **The load is closed-loop.** Each of oha's `c` connections waits for its response before sending the next request.
  Once a server is saturated, latency is mostly queueing: mean latency ≈ c ÷ throughput (Little's law). At high
  concurrency the latency columns therefore largely restate the throughput column. oha does not correct for
  coordinated omission in this mode. An open-loop test at the same fixed request rate for both servers compares
  latency at equal load; Part 1 does **not** do that, Part 2 does.
- **One payload, repeated** (Part 1). Every request is the same 210-byte body, so caches and branch predictors stay
  warm. Real traffic varies. Part 2 draws from 1,000 different requests.
- **Defaults only.** No Node or V8 flags (GC and heap sizes are defaults). Rust uses the system allocator. Tuning
  either side could change the results.
- **Headers are not identical.** Node sends `Connection: keep-alive` and `Keep-Alive: timeout=5` (about 47 bytes per
  response) that axum does not.
- **Invalid UTF-8 bodies** are handled differently on Part 1's `/bid` route, and no test or benchmark exercises
  them: axum's `String` extractor rejects them with a plain-text 400, while Node's `toString('utf8')` replaces
  invalid bytes with U+FFFD and passes the string on. Part 2's route passes the raw bytes to the same Rust function
  on both sides.
- **The VM's CPU speed is not stable** (see Diagnostics). Differences smaller than the min–max ranges in the tables
  should not be treated as real.
- **The V8 profile is a sampling profile**, with profiler overhead. It cannot show the napi call as its own frame, and
  it does not see inside the kernel. It was not used for the comparison tables.

Part 2 adds its own:

- **Synthetic traffic.** The 1,000 requests come from a generator, not from an exchange, and are not a model of
  any real exchange's traffic (its sizes, fields or mix). The 84% bid rate is a property of the generated data.
- **A toy bidder.** One seat, one image creative per line item, fixed first-price shading (85% of value), USD
  floors only, and a scan over every line item of the requested size. No budgets, pacing, frequency caps or
  models.
- **Not covered:** video, audio and native ads (they get no bid), gzip, privacy signals (COPPA, GDPR, US privacy),
  and win/billing notice handling.
- **No network.** `tmax` normally has to cover the round trip to the exchange. On loopback the whole 100 ms is
  left for queueing and processing, which is far more generous than a real deployment.
- **The open loop's "answered" share is an upper bound under overload.** oha starts each request's 100 ms timeout
  when it sends it, and holds requests back while all 500 connections are busy. The latency percentiles do include
  that wait (`--latency-correction`), so trust them over the "answered" column when a server is overloaded.
- **500 connections** is one choice. An exchange may open more or fewer connections, which changes how much a
  server can queue.
- **2 runs per cell** (memory: 1), and some ranges are wide: the Node cluster at 25k req/s had 0 timeouts in one run
  and 8,160 in the other.
